## 0. 一句话定位

面向**全集团及旗下分公司**的 AI 创新平台官网——作品展示、活动、报名、投票、

## 4. 数据模型（PostgreSQL，第一落点）

> 概念设计，字段后续细化。核心原则：**全集团数据以 PG 为唯一权威**。

### 4.1 用户与组织（飞书 SSO 快照）
- `users`：飞书 `open_id`、姓名、邮箱、公司/部门（快照）、角色（employee / reviewer / admin）、状态
- `departments`：部门树（公司 → 分公司 → 部门），供统计与分权

### 4.2 内容
- `works`：作品条目（标题、作者、分类、活动来源、封面、简介、detail.link、原始数据字段）
- `activities`：活动（类型、时间、状态）
- `sessions`：期数（第 02 期等）

### 4.3 业务数据（全过我们）
- `registrations`：报名（姓名、部门、联系方式、报名活动、是否愿意分享、分享方向、备注、时间、审核状态）
- `votes`：投票（user_id、activity_id、work_id、时间、唯一约束防重复投票）
- `reviews`：评审记录（评审人、作品、维度、结论、备注、时间）

### 4.4 制品（作品资源，C6 刚需）
- `artifacts`：作品资源文件（属于哪个 work、类型：video/miniprogram/skill/mcp/source/static、版本号、存储路径/URL、大小、校验、下载次数、本地调用指引）
- `work_deployments`：部署登记（作品、环境：innernet/public、平台流水号、状态、URL）——对接基建「发布记录」

### 4.5 观测
- `access_logs`：访问统计（页面、用户、公司/部门、时间、UA）

## 5. 接口清单（概念）

- 认证：飞书 SSO 登录 / 回调 / 登出 / 当前身份
- 公开：works、activities、works/{id}、artifacts/{id}/download、votes（登录后投票）、register
- 后台（鉴权 reviewer/admin）：作品增删改、作品资源上传/版本、活动管理、报名审核、投票统计、评审、用户/部门、访问统计、报表
- 对外出接口：公网宣传审批记录（对接基建部署、人工鉴权后登记）

## 6. 分期路线（建议，可按反馈调整）

### Phase A · 数据与工程地基
- 定 PG 环境（本地 `E:\PostgreSQL` 16.4 已确认；生产连接方式定案）
- 初始 schema + 迁移脚本
- 后端引入 DB 连接、把报名/作品/活动第一落点切到 PG

### Phase B · 登录与身份
- 飞书 SSO 接入
- 用户/部门快照落库
- 角色分权雏形

### Phase C · 报名全链路 + 投票
- 报名改造为 PG 主库
- 投票功能（身份防刷）

### Phase D · 管理后台
- 作品/活动/报名/投票/评审/制品/用户的后台管理界面
- 统计报表

### Phase E · 制品分发（C6 刚需）
- 对象存储接入
- 上传、版本、下载、本地调用指引
- 作品详情对接资源下载入口

### Phase F · 部署接线与上线
- 官网作为内网应用挂入「内网应用网站发布」
- 公网宣传人工鉴权 + 出接口登记（C7）
- 访问统计/观测

> 排期原则：Phase A/B 是硬序；C/D/E 视人力并行；F 贯穿或收尾。
> **前端视觉审美（C8）不进入本计划**，另行按原班子节奏处理。

## 7. 仍需对齐 / 交接给基建的问题

1. **数据库归属**：对象存储是谁提供（云 OSS / 基建对象存储 / 自建 MinIO）？——影响 Phase E
2. **PG 生产连接方式**：我们自管一台 PG，是否在基建 K8s 里给它一个实例/持久卷，还是独立机器？——影响 Phase A/F
3. **飞书 SSO 应用凭证**：哪个自建应用负责登录（现 `LarkClient` 只做 Bitable 写入，需新增登录权限）？
4. **「出接口」契约**：公网宣传那条接口，能部署什么、返回什么、我们怎么登记（C7）
5. **带后端作品托管**：与基建「内网应用网站发布」的关系，是平台引导作者自助发布、我们登记地址（推荐）？——待确认
